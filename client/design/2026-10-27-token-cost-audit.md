# 正文生成 Token 消耗审计与低风险优化

日期：2026-10-27

## 结论

本轮保留既有质量门槛：逐节事实抽取、跨节语义审查、事实修复、图片/表格/承诺保护、自然文风审查、篇幅验收、Word 转换与断点恢复。未调用付费模型或降低用户正式模型。按用户要求新增独立 GLM 免费测试档案，保存时验证原活动配置不变；密钥不写入源码、命令行参数或报告。免费接口只用于联调，不据此宣称整书质量等价或人民币降费已验收。

最大可确认浪费来自“一致性审计主 Agent 反复写 shell/Node 脚本遍历同一份事实台账”，而不是正文首稿本身。已将这一步改为程序化的全量结构化比对和定点工具，并在一致性阶段关闭通用遍历工具。

## 历史真实任务离线回放

回放脚本：`scripts/replay-content-token-cost.cjs`。脚本只读本地任务的 session、事实台账和修复清单，只输出计数、服务商已报告 Token 字段和字符规模；不输出正文、Prompt、响应、密钥或本机路径。

最近一次 65 节正文任务可观测到：

- 主 Pi session 共 121 个 assistant 回合：fresh input 200,371、cache read 13,619,840、output 74,675。
- 一致性阶段占 85 个 assistant 回合：fresh input 147,067、cache read 11,417,856、output 44,649。
- 80 个回合调用 bash；按命令形态离线归类为 45 次检索/读取、31 次 Node/JSON 脚本、4 次其他。仅这些回合已报告 fresh input 160,424、cache read 9,526,656、output 22,197。
- 事实台账含 65 节、2,201 条事实、60 个问题；43 节事实修复成功。
- 事实使用“小节字典 + 紧凑元组 + 数值事实引用”编码后，最终生产构建器的全量语义 JSON 为 167,469 字符；连同规则和 5,747 字全局事实，保守估算约 105,856 input tokens。该估算只用于上下文预算，不当作账单。
- 43 节中自然文风审查为 pass 31 节、needs_revision 12 节、unknown 0 节。变化节 HTML 合计 262,270 字符，仅用于量级比较，不换算或声称等于 Token。

这些数字不是整份标书账单：旧版本未按业务 task/stage 持久记录直接 `aiService` 请求；session 只覆盖 Pi 主会话。`cache read` 也不代表固定折扣，各服务商计费规则不同，不能把它与 fresh input 简单相加估价。

## 已实施优化

### 1. 一次全量语义比对，替代主 Agent 循环遍历

- 将所有类别的完整事实一次交给结构化模型审查，保留跨类别和同义主体判断，避免九分类隔离漏检。
- 小节 UUID、编号、标题只在字典中出现一次，2,201 条事实通过别名元组引用；每条事实另有唯一数值引用。模型候选只能返回 `fact_ref`，程序从原始事实回填小节、段落、取值和摘录，既不接受伪造字段，也不要求模型重复输出长证据文本。
- 缓存哈希同时绑定规则版本、system 规则、全局事实和完整事实；任一变化都失效。
- 请求前按当前 `context_length_limit`、8,192 输出预算和安全余量做估算；超限时不截断事实、不调用该请求，明确回退原始台账完整复核。
- 输出证据必须引用输入中存在的 `fact_ref`，程序再回填真实小节 ID、段落 ID、取值与原文摘录；模型不能自行重抄或伪造证据字段。失败时明确回退完整原始台账，不能把失败当成“无问题”。
- 外层 JSON 重试设为 0；仍保留已有的一次 JSON 修复，不重复发送整份台账多轮。
- 一致性阶段只保留 `read/write/edit` 及 `search-sections/recheck-sections/repair-sections` 等业务工具，不再开放 bash/grep/find/ls 绕过结构化流程。`read` 保留作结构化审查失败时的显式原始台账兜底。
- 主 Agent 默认只读取独立的《正文一致性问题清单》（全部逐节明确问题、失败小节及必要证据）与语义候选，不再因读取问题而顺带把 2,201 条事实拉进主上下文；完整台账只在全量语义审查失败时兜底。

真实台账离线计划为 1 次全量语义请求；旧主 session 的 85 个一致性回合不能直接等价为 1 次请求，因为仍需主 Agent 复核候选并执行必要修复。实际节省须由新任务持久用量记录验证，未虚报百分比。

免费 GLM 的一次旧版全量捕获请求实际报告 prompt 96,037、completion 298、total 96,335 tokens，耗时约 24.4 秒。首个响应 JSON 括号错误；既有小修复链只发送 415 input + 298 output，没有重传 96K 全量事实。修复后的候选因模型重抄的摘录/取值不精确而被严格证据门禁拒绝，未冒充真实通过。最终协议因此改为模型只返回数值 `fact_ref`，程序回填原始证据；真实付费节省与最终检出质量仍须同模型、同资料 A/B 验证。

### 2. 事实修复与文风修复合并

- 逐节一致性抽取的同一次 JSON 已包含 `naturalness` 审查，不新增审查请求。
- 仅 `pass + 无事实问题 + 当前 HTML SHA256 匹配` 可跳过后续整节去痕；missing/unknown/旧哈希/仍有事实问题均不能通过。
- 已有事实修复任务若同时存在明确文风问题，将具体段落问题附到同一个修复子任务；不再形成“事实修复 → 完整复核 → 整节文风重写”的三段链。
- 事实修复后仍只对真实变化节做一次结构化复核；未变化节按哈希恢复，不重复付费。复核失败或仍有事实冲突时保留正文并回到定点修复，不能以文风通过掩盖事实冲突。

本次历史回放中有 12 个“事实修复且文风 needs_revision”的小节可把文风处理并入已有修复请求；31 个明确 pass 的变化节在复核通过且哈希一致后无需完整重写。这是离线候选数，不是已发生的账单节省。

### 3. 新任务完整用量台账

- 直接 `aiService` 和 Pi OpenAI 代理都按真实 HTTP 请求记录；stream/normal/失败各记一次，请求 ID 去重。
- 按业务 task 和 stage 持久汇总 input、cached input、fresh input、output、reasoning、total、成功/失败/未知用量请求数。
- 只保存请求元数据和 Token 数，不保存 Prompt、响应、API Key 或业务文件路径；文件原子写入。
- 服务商未返回 usage 时记为 unknown，不显示误导性的 0；旧历史任务返回 null，明确不可追溯。

### 4. GLM OpenAI 兼容

当 `text_model_provider === "glm"` 时输出上限使用 `max_tokens`；其他服务商仍使用 `max_completion_tokens`。没有修改 DeepSeek 等其他 provider 的参数策略。

## 缓存与预热

历史任务的 cache read 很高，说明服务端确实报告过缓存命中，但无法仅凭本地日志判断预热请求是否带来净费用收益。不同服务商的缓存折扣、写缓存费用和有效期不同。本轮没有新增预热调用，也没有在缺乏同 provider 前后 A/B 的情况下删除既有预热或宣称固定节省比例。

## 验证与限制

- 纯函数/离线测试覆盖：跨类别同义主体、完整事实证据校验、全局事实变化使缓存失效、失败回退、变化节哈希恢复、事实与文风同请求、任务用量去重和隐私字段。
- 离线真实回放覆盖 65 节/43 修复节的历史产物；另通过临时内存中转做了受控免费 GLM 协议验证，未调用用户付费配置。
- 全量事实请求若超出用户所选模型上下文，会明确失败并回退原始台账完整复核，质量优先，不截断事实冒充成功。
- 新用量台账从本版本后的请求开始；无法补造旧版直接请求的精确用量。
- 最终节省取决于 provider 的缓存/计费规则、实际候选数量、修复节数量及模型输出，需用同一模型、同一资料的新旧 A/B 才能给出可信百分比。
